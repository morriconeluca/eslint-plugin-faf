# Contributing to eslint-plugin-faf

Thank you for contributing to `eslint-plugin-faf`! This document guides you through setting up the local development environment, project structure, writing rules, and releasing updates.

---

## Codebase Architecture

The project is structured to enforce strong type-safety, maintain clean boundaries, and follow strict linting patterns according to the Fractal Architecture Framework (FAF).

```text
├── .changeset/               # Automatic packages version tracking configuration
├── .github/workflows/ci.yml  # GitHub Actions pipeline
├── .husky/                   # Git hooks (pre-commit lint-staged, commit-msg commitlint)
├── .vscode/                  # Shared VS Code workspaces settings & recommendations
├── __test__/                 # Architectural and graph fitness tests
├── faf.config.ts             # Local FAF taxonomy settings for self-linting
├── src/                      # Plugin source code
│   ├── main.ts               # Entry point exposing rules and configs
│   ├── main.type.ts          # Plugin type definitions (TFafPlugin)
│   └── _rules/               # FAF rule Category
│       ├── _rules@shared/    # Shared utilities Fractal Branch
│       └── <rule-name>/      # Folder Fragment for each rule
│           ├── index.ts      # Access Node (exports the rule module)
│           ├── <name>.rule.ts # Rule implementation
│           └── <name>.spec.ts # Rule unit tests
├── tsconfig.json             # Workspace-wide type checking compiler settings
├── tsconfig.build.json       # Production emit compiler settings
├── tsup.config.ts            # Tsup dual bundling (ESM + CJS) settings
├── eslint.config.ts          # Flat type-checked ESLint configuration
└── .prettierrc               # Prettier formatting configurations
```

### Dual Build System

ESLint plugins must support both CommonJS (CJS) and ES Modules (ESM) to run across diverse developer toolchains. We use **`tsup`** (powered by `esbuild`) to bundle and output both versions:

- **CommonJS** is compiled to `dist/main.cjs`.
- **ES Modules** is compiled to `dist/main.js`.
- **Typings** are generated into `dist/main.d.ts` and `dist/main.d.cts`.

### Dependency Fitness Function

Powered by `dependency-cruiser` inside `__test__/dependencies-graph/dependencies-graph.test.ts`, this test ensures:

- **Zero circular dependencies** between rules.
- **No orphan modules** (every rule must be exported by `src/main.ts`).
- **No incorrect internal imports** (e.g. source files referencing compiled `dist/` artifacts).

## Local Development Setup

### 1. Prerequisites

- Node.js (v20+ recommended)
- npm

### 2. Installation

Clone the repository and install the local dependencies:

```bash
git clone https://github.com/lucamorricone/eslint-plugin-faf.git
cd eslint-plugin-faf
npm install
```

---

## Development Scripts

- **Build**: Compiles rules into the CJS/ESM dual bundle inside the `dist/` directory.

  ```bash
  npm run build
  ```

- **Test**: Executes rule tests once.

  ```bash
  npm run test
  ```

- **Lint**: Performs type-checking (`tsc --noEmit`) and lints workspace files using ESLint.

  ```bash
  npm run lint
  ```

- **Lint Fix**: Resolves auto-fixable ESLint violations.

  ```bash
  npm run lint:fix
  ```

- **CI pipeline check**: Prepares build, verifies format, and runs rule tests.

  ```bash
  npm run ci
  ```

## Writing Custom Rules

ESLint rules analyze the AST (Abstract Syntax Tree) generated by parsers.

### 1. Create the Fragment folder (`src/_rules/my-rule/`)

Each rule must be encapsulated in its own folder under `src/_rules/` with three files:

#### Rule implementation (`src/_rules/my-rule/my-rule.rule.ts`):

```typescript
import type { Rule } from 'eslint';

const rule: Rule.RuleModule = {
  meta: {
    type: 'problem',
    docs: {
      description: 'Describe what this rule does.',
    },
    schema: [], // Configuration schema
  },
  create(context) {
    return {
      // AST Node visitors go here
    };
  },
};

export default rule;
```

#### Sibling Unit Test (`src/_rules/my-rule/my-rule.spec.ts`):

Ensure tests import the rule file directly, **not** through the `index.js` Access Node, to avoid peer dependency violations:

```typescript
import * as tsParser from '@typescript-eslint/parser';
import { RuleTester } from 'eslint';
import { afterAll, beforeAll, describe, it } from 'vitest';

import myRule from './my-rule.rule.js';

// Bind Vitest globals to globalThis so RuleTester can find them
Object.assign(globalThis, { afterAll, beforeAll, describe, it });

const ruleTester = new RuleTester({
  languageOptions: {
    ecmaVersion: 2020,
    parser: tsParser,
    sourceType: 'module',
  },
});

describe('my-rule', () => {
  ruleTester.run('my-rule', myRule, {
    invalid: [
      {
        code: 'const badCode = 1;',
        errors: [{ message: 'Describe the expected error message' }],
      },
    ],
    valid: [
      {
        code: 'const goodCode = 1;',
      },
    ],
  });
});
```

#### Access Node (`src/_rules/my-rule/index.ts`):

```typescript
export { default } from './my-rule.rule.js';
```

### 2. Register the Rule (`src/main.ts`)

Add your rule to the `rules` export map and `configs.recommended.rules` map in `src/main.ts`:

```typescript
import myRule from './_rules/my-rule/index.js';

export const rules: Record<string, TFafRuleModule> = {
  // ...
  'my-rule': myRule,
};
```

## Submitting Pull Requests & Release Flow

1. Commit message guidelines conform to **Conventional Commits** (validated by git hooks).
2. Before pushing your branch, run the local CI check: `npm run ci`.
3. Document your changes for version updates using Changesets:

   ```bash
   npx changeset
   ```

4. Push and open your PR.
